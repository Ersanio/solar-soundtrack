# Text and i18n

Read before adding or changing any text a porter reads: a template, a `$localize` message, a
diagnostic, a command name or parameter description, or `web/src/locale/messages.en.json`.

The code carries IDs, not words. Every user-facing string goes through Angular's i18n
(`@angular/localize`) with a custom ID, and its source text is that ID and the message's
placeholders — the source locale, `en-x-ids`, is a language of IDs. The English is
`web/src/locale/messages.en.json`, a translation like any other: the build swaps it in for every
message (`localize: ["en"]` in `angular.json`), so the page never runs `$localize` for a message.
No other locale is set up.

## Changing and adding text

- **Words** are changed in `messages.en.json` and nowhere else. A running `npm start` picks the
  change up on the next reload. `npm run start:ids` serves the app in the source locale, where
  every message shows its ID and its values in place of the English.
- **A new message** is written in the code by ID (below). `npm run i18n` then adds the ID to
  `messages.en.json` with its source text as a stub, and drops IDs the code no longer has; the
  English goes over the stub. `npm run check` fails while a stub is left.
- **A value or an inline element** added to a message, or taken out of one, changes both halves:
  the code holds the structure, the English the words around it. `npm run check` fails while the
  two disagree on a message's placeholders.

## Writing a message in the code

- **Templates**: `i18n="@@id"` on the smallest element holding a whole sentence, its content the
  ID and then the message's structure — each interpolation, and each inline element (`<code>`,
  `<strong>`, `<span>`) with its attributes and nothing inside but more of the same.
  `<ng-container i18n>` for text beside an icon. `i18n-title`, `i18n-label`, `i18n-heading`,
  `i18n-note` or `i18n-legend` on a static attribute whose value is the ID and its interpolations
  (`title="mixer.mute.title {{ channel.index // i18n(ph='channel') }}"`).

  ```html
  <p i18n="@@inspector.fir-designer.a-f1-on-line" class="text-warn text-xs leading-relaxed">
    inspector.fir-designer.a-f1-on-line <code class="text-ink"></code>
    {{ later.line // i18n(ph='line') }} {{ later.filter // i18n(ph='filter') }}
  </p>
  ```

  ```json
  "inspector.fir-designer.a-f1-on-line": "A {$START_TAG_CODE}$F1{$CLOSE_TAG_CODE} on line {$LINE} replaces these coefficients with {$FILTER} — so they only apply until it runs. AddmusicK does this silently."
  ```

  Identical elements share one placeholder name and are used in turn, so the English writes one
  `{$START_TAG_CODE}…{$CLOSE_TAG_CODE}` pair per `<code>` in the template.

- **ICU**: a plural or a select is a message of its own, the only thing in an
  `<ng-container i18n="@@id">`, each case's text the ID and its interpolations. The English has
  cases of its own: `{VAR_PLURAL, plural, =1 {1 problem} other {{COUNT} problems}}`.
- **Bound text** cannot take an `i18n` attribute. A ternary between two strings becomes a
  `protected readonly text = { … }` of `$localize` messages on the component, declared after its
  `inject()` fields; a ternary inside a sentence becomes `@if` branches or an ICU `select`.
- **TypeScript** writes `` $localize`:@@id:id ${count}:count:` `` — the ID twice, then each
  placeholder, named, so the English reads `{$count}`. Module-level messages are fine: the build
  inlines every one, and the harnesses load the English before anything else
  (`scripts/localize.ts`).
- **Plurals** in TypeScript are two messages (`.one`, `.other`) chosen in code, since `$localize`
  takes no ICU.
- **Whole sentences.** A message is never glued from fragments round a condition; each branch gets
  a message of its own, even where most of the words repeat.
- **Text is never a key.** Where code compares a string a porter reads, it compares a stable key:
  `FIR_PRESETS` match on `id`, and `loop-wrap.ts` tells a note by its `noteLength`.

Every interpolation in a template is named with `// i18n(ph='…')`, so the English reads `{$LINE}`
rather than `{$INTERPOLATION_1}`; Angular upper-cases these names, where TypeScript's keep their
case. Prettier puts a named interpolation on lines of its own. An expression used twice in one
message has to be written the same way both times, whitespace included, or it becomes two
placeholders — `npm run check` reports the mismatch.

## IDs

`group.segment[.segment…]`: lowercase letters and digits, hyphens inside a segment. The group says
**where the porter reads the text, not which file holds it** — the same rule as a diagnostic's
prefix. Attribute texts end in their role (`.title`, `.label`, `.heading`, `.note`); TypeScript
plurals end in `.one` / `.other`.

| Group                          | Text                                                                                  |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| `amk`, `sst`                   | diagnostics, by code and variant: `amk.0058`, `amk.0096.rate`, `sst.0502.other`       |
| `command`                      | the shared command vocabulary: names, note lengths, units, intervals                  |
| `inspector`                    | the command inspector and its panels, the parameter table, FIR presets, GAIN modes    |
| `loops`                        | the loop inspector                                                                    |
| `palette`                      | the command palette: categories, blurbs, caveats, refusals, availability              |
| `roll`                         | the piano roll: toolbar, refusals, tooltip, drag readouts, percussion                 |
| `source`, `editor`             | the source view and its hover; the editor pane's tabs                                 |
| `samples`                      | the sample browser                                                                    |
| `transport`, `mixer`, `topbar` | the transport, the channel mixer, the top bar and its history buttons                 |
| `output`                       | the output pane: build, problems list, hex dump, stats, ARAM                          |
| `status`                       | the status bar and the status line                                                    |
| `theme`, `changelog`, `update` | the theme picker, the changelog popup's chrome, the update banner                     |
| `error`                        | failures shown to the porter: driver, export, BRR and sample bank validation, storage |
| `common`                       | shared components                                                                     |

`scripts/i18n-catalog.mjs` holds the group list and rejects any other, any ID not in this form — a
`$localize` without `@@id` gets a numeric one, so that is where a missing ID surfaces — and any
message whose source text has words besides its ID. One ID may serve several places when the
source is identical; extraction fails on one ID with two.

## Diagnostics

Every diagnostic has an entry in one of two catalogs in `@amk/core`, since `SST` codes are raised
from three packages and the app: `messages/amk.ts` for `AMK`, `messages/sst.ts` for `SST`. Each
entry is keyed by code, or code and variant, takes the diagnostic's values, cites the AddmusicK
line it ports, and is a function so nothing builds a message at import. Its words are under the
same ID in `messages.en.json` (`amk.0058`). The call site states the code and calls the entry —
`this.error("AMK0058", AMK["0058"](name))` — and the two must agree. A new diagnostic adds its
entry to the catalog of its prefix and its English to `messages.en.json`.

## Packages, workers and the worklet

The packages use `$localize` as a host-provided global and import nothing from Angular, so the
package boundary in `eslint.config.js` stands; each package's tsconfig names its types. The build
inlines their messages with the app's.

A worker and the AudioWorklet have no `$localize`. Their import graph — `worklet.ts`,
`protocol.ts`, `driver-state.ts`, `wasm-host.ts` and `note-audition.ts` in `@amk/spc`, and
`spc-core.ts` and `measure-clock.ts` in the app — holds no message, and its errors are written in
English in the code.

## Not marked

The changelog's entries (its popup is), `index.html` and the web manifest, which Angular's i18n does
not read, `README.html` and `COMMANDS.html`, MML spellings, dialect tags such as `#amk 4`, colours,
and number formatting. `listOf`, `capitalise` and lowercasing a label for a sentence are English
grammar, and would need rework before a second locale.

## Decisions already made

- **English in the code beside its ID** — templates and `$localize` carried the words, and the
  catalog was generated from them: a list to search, not a file to edit. Changing a word meant
  finding its ID there and then its source. The code carries IDs and `messages.en.json` is the
  English, edited in place and swapped in at build time, which also takes `$localize` and its
  message metadata out of the page.
- **Angular's default placeholder names in templates** — interpolations went unnamed to spare the
  templates Prettier's line breaks, so a message read `{$INTERPOLATION_1}` and only the template
  said which value that was. Each is named now; the line breaks are the price.
- **Diagnostic text at its call site** — each `error()` carried its own English, so one code's
  texts were spread through `parser.ts` and the `SST` ones through three packages. Each code and
  variant has one entry in a catalog in `@amk/core`, with the AddmusicK line it ports cited beside
  it, and a repeated text is one message.
- **Strings a porter reads used as keys** — `builtInTaps` found a FIR preset by its name, and the
  loop wrap told a note by `command.name === 'note'`. Translating either would have changed what
  the code does; both match on a stable key now.
