# Harnesses

Fifteen byte-level checks, each a standalone esbuild-bundled Node script with its own npm script.
There are no `.spec.ts` files anywhere in the repository — `npm run test` is Angular scaffolding and
currently runs nothing. These are the real suite.

Run one by name (`npm run selftest`). They take no filter flags, so narrowing a run means editing
the harness. `npm run check` runs all fifteen, grouped:

| Group               | Harnesses                                         |
| ------------------- | ------------------------------------------------- |
| `check:compiler`    | `selftest`                                        |
| `check:tokens`      | `tokentest`, `edittest`, `palettetest`            |
| `check:spc`         | `adsrtest`, `instrtest`, `brrtest`, `firtest`     |
| `check:integration` | `spctest`, `audiotest`, `worklettest`, `walktest` |
| `check:app`         | `charttest`, `normalizetest`, `rolltest`          |

Eleven of the fifteen import a value from two or more `@amk/*` packages — every one but `adsrtest`,
`edittest`, `selftest` and `tokentest` — which is why they all live here rather than one per package,
and why they share `harness.ts` rather than each carrying a copy: copies drift. Recount that rule
rather than bumping the number when one is added.

| `selftest`      | Compiler output, byte for byte. Also that diagnostic spans land on the offending character, not merely near it. | `audiotest`     | MML → SPC → actual PCM through the real wasm host. **This is what proves the whole pipeline**: a wrong compiler, layout, sample directory or CPUIO handshake produces silence. It also pins that **muting does not change how fast the song plays**: the mixer takes a voice's volume and leaves `$5E` alone, because disabling a channel makes the driver's main loop cheaper and a song at the one-tick-per-pass ceiling turns that into a 29% speed-up. Checked on eight channels at t254, where an easy song shows nothing at all. It also pins that the voice the tick count runs on is one the driver plays: a song whose lowest channel is `#1` is counted off voice 1 and ticks exactly as the same music on `#0` does — the latch reads the track pointer's high byte as the driver does (`main.asm:2315`), because a whole-word read lands in the driver's start-up hot-patch trick (`main.asm:2104`), takes voice 0, and counts nothing for the rest of the song. Last, it pins **auditioning one note**: that the frames handed to the driver are the ones `emitNote` would write for a note of that length, that the note is played under the instrument and the `q` the song left standing rather than under a default, that a channel the song never uses is still audible, and that the emulator is left exactly as it was found — the caller's SPC image unwritten and the song rendering byte for byte the same afterwards, which is what "a note can be auditioned while the song plays" rests on. Last of all, that the **mixer's mask reaches the fast-forward**: a silenced channel is out of the echo the note lands on, while the same song with no echo renders the same either way to within a thousandth of the signal — the echo buffer is the only route a mute has in, since every other voice is halted before the note is handed over — and the tick the fast-forward reached does not move, because `$5E` is still untouched. The target channel's own bit is ignored, in both spellings: a note on a silenced channel is refused before an emulator is asked for, and honouring the bit here would take that voice's volume and then hand it straight back. | `charttest`     | Stacked-bar geometry for the ARAM bar, the shared plot space, `clamp`, and the piano roll's lanes, window arithmetic and percussion set. Five roll claims live here, none of them visible in a screenshot: that the playhead's clock absorbs a steady lag instead of re-correcting it on every anchor, which is the difference between a smooth scroll and one that jerks ten times a second; that "all octaves" widens the pitch range without conjuring a drum lane the song never plays; that sweeping a playhead rebuilds the mark window about twice per whole note rather than once per frame, which is what keeps a scroll off the DOM; that a drum the porter takes off the percussion lanes falls back to the note the driver's own table gives it rather than vanishing, having neither a lane nor a key; that a pitched note draws on the pitch it was **written** at rather than the byte `h` or the instrument's transposition made of it, with the keyboard growing to take in a written `o0` or `o7` the driver's o1 c–o6 a has no row for; and that an empty stored percussion set is kept rather than read as "no opinion", which would make turning everything off undo itself on reload. It also pins what a bar can hold: that the compact `C6` a bar is labelled with and the `o6 c` down the key column can never name different keys, that a row too short holds nothing rather than half a letter, and that as a bar narrows its glyphs only ever drop — never grow, which is what happens when the glyphs are allowed the room the name gave up, so a bar loses its note and gains an icon. It also holds the transport's clock (`state/song-clock.ts`): that a song with no `t` is still clocked at the driver's t53 rather than treated as tempo-less; that a fade is priced tick by tick and comes to **exactly** what its inspector label says, so one song can never have two lengths; that a fade cut short keeps the delta its _written_ duration gave it, since re-deriving one from the ticks that survive is a different fade and reads entirely reasonable; that `t255` stalls rather than dividing by zero; and that the segment table joins up at every boundary, without which the readout jumps at each one while still looking monotone and plausible either side of it. It pins the **scrub bar's** time axis, which a drag rides on: that the whole song fills the bar at any pane width and any song length, and that the tick a scrub commits to is exactly the tick under the pointer — one that landed merely near it would drop the song a note away from where it was dropped every time, with nothing on screen to say so — and that a song of no ticks answers 0 rather than an `x` of `NaN` on every bar of the minimap, which renders blank and says nothing. It pins that bar's **minimap** too, where every claim is a note that is not drawn: that two channels through one pixel of a row are two bars and one channel's two are one, since the colour is which channel a bar is and a dedupe blind to it drops the narrower note out of the picture altogether — two channels on a drum lane is the ordinary way that happens; that the wider survives whichever order the pair arrives in; that a silenced channel is dimmed at the roll's own value rather than dropped, and comes back before every audible bar so a live one is never veiled; and that every bar's id is its own, which is what `track` needs and what a channel kept out of the key would break. It carries the roll's **pages**, the second of its two ways of following the song: that a turn leaves the music just played still on screen rather than dropping the playhead against the key column, that the opening page starts _before_ the first tick so a song is drawn with the same lead-in every later page opens on — without which the margin appears out of nowhere at the first turn and a scroll back to the beginning shows a space that then vanishes, that re-anchoring the page grid on a parked view reproduces that view's camera exactly — without which a scroll is undone by the page boundary the instant the wheel goes quiet, the notes snapping back by precisely as far as the wheel had moved them, that the playhead can never be drawn off the pane it is in, that a page never turns backwards as the song runs forwards, and — the one with no visual tell — that every page a sweep can produce lies inside the window the marks are built for, since a roll whose marks are built for the wrong span scrolls perfectly smoothly over blank music. And the roll playhead's **velocity**: extrapolating between anchors at the tempo byte rather than at the clock's measured slope leaves it more than a quarter note ahead of the notes it is drawn over, scrolling perfectly smoothly the whole way — the failure with no visual tell at all. | `walktest`      | The song-data walker, `@amk/spc/song-walk`, which is the only thing the piano roll draws from — and a walker that mis-frames one command draws a plausible roll that is quietly wrong, with no visual tell. Three assertions carry it. **The two packages are pinned together**: `@amk/spc` may not reach `@amk/tokens`, so each states how long a VCMD is, one about emitted bytes and one about source text, and this asserts they agree at every `$DA`-`$FE`, every `$FB` count and every `$FA $FE` chain length — the only thing that makes the restatement safe. **`$FB`'s arguments are not notes**: an arpeggio's operands sit in the `$80` range without being notes, so pricing `$FB` at a fixed length invents a chord out of nowhere and still yields a timeline that reads as reasonable. **The emulator is the oracle**: tick totals matching `stats` only prove the walk agrees with AddmusicK's own prediction and both could be wrong together, so the real driver is run and the note the walk predicts is compared against the one each voice's track pointer is actually on. It also pins that `@29 o2a1b2c3` is one drum then two pitched notes on `#0` but three drums on `#6`, which is the channel-dependent behaviour that makes walking bytes worth doing at all. It pins the **command** map, which is what makes a glyph on a bar clickable: that every entry addresses the byte the scanner says was written at its span — off by one and it addresses an argument, and still walks and still draws — and that no note is in both maps, which would make a note a command in force on itself. And the exactness that map exists for, in the two shapes no reading of the source can reach: `v255 (1)[ c8 d8 e8 ]2 v200 (1)5` turns three written notes into 21, the first six under `v255` and the rest under `v200`, where the command that decides it is not inside the body at all; and a command at the _end_ of a `[ ]` body is in force for that body's own notes on the second pass and not the first, where one at the head is in force on every pass and would pass under any answer at all. It pins that `$DF` takes the vibrato slot away rather than filling it, that a drum loaded by its own note byte leaves no stale `@` behind and names the loading note in `drumFrom` instead — and, through `state/commands-in-force.ts`, that a note still on a drum's sample is shown under the `@` that loaded it, when the loading byte sat inside a `[ ]`, was replayed by a `*`, or was called from another channel, where no reading of that note's own text could find it. It pins the other half of that question, which is which of the commands acting on a note the note **puts** in force rather than inherits — the roll plates those glyphs and the two mistakes available are both silent: comparing `origins` arrays instead of the commands in them lights up every channel's next note after any song-wide `t`, since `recordOrigin` invalidates all eight, and taking "the note before" from the note list instead of from the channel lights up alternate notes on every song with more than one voice, so a song is written for each. Also that a `[ ]` re-running a command that changes nothing is not a second definition where one that alternates is a definition every time round, that a slot a `$DA` cleared is put back in force by the byte re-enabling it, and that one `v200` inside a `(1)[ ]` called from two channels is put in force on both — which is why the colour saying so cannot be a channel's own. It pins that a channel that never writes an `@` plays `@0` (`main.asm:2321`), that one song reaches every slot the walk tracks, and that consecutive notes under unchanged state share one `origins` array — the roll builds a view model off those, so a fresh array per note is a fresh view model per note. It pins the note map's **written** pitch beside the byte — `@2 o5 g` is `$B2` on the wire and `$B7` as written, `h12 o0 c` is `$80` and `$74` — which is the row the roll draws on and the one thing the walk cannot recover from bytes; that `$FA $02` is reported as a channel's tune and moves no byte; and that a song-wide `t` or `$E4` on one channel is reported by the next note on every channel, not only the one that ran it. It pins that a command above the first `#N` is in force on the lowest channel the song declares and on no other, and that a channel written in two blocks is one track — six notes on `#0` in time order, the second block's under its own `@`. It also carries the tempo map: that a `t` inside a `[ ]` is recorded **once per iteration** — an execution and not a byte, which is the thing the compiler cannot say and the whole reason the map exists — and the cross-check that the clock retimes no ordinary song relative to `stats.playback`, with the one class that does differ pinned as the exact ratio 55/54 rather than left to be found later. Last, it pins the **measured** clock, which is the only figure in the app that had to be played to be found: an easy song measures within a percent of the prediction, eight channels at `t254` fall more than 1.5x short of the rate they ask for, a short song whose first tick zeroes a 30 KB echo buffer still measures at tempo — the lead-in before the first tick is a cost and not a rate, and stays in the pass length because it is heard — a song of one-tick ties and a song of nothing but one-tick notes both measure at tempo, which a count taken off the note duration counter reads 8.5% and three times slow — `$70+2n` is reloaded with the 1 it was already holding, so the tick that fetched such a note moves nothing to see — and `measure-clock.ts` prices a driver tick exactly as `@amk/tokens` does — the same restatement guard `vcmdLength` lives under, and what `SST0503` rides on. | `tokentest`     | The MML scanner, and the command model on it. Its load-bearing assertion is **restartability**: stepping line by line with the state carried across must equal scanning the whole document. CodeMirror restarts the scanner at arbitrary lines, so a state machine that secretly depended on having seen the top of the file would pass a whole-document test and mis-colour text much later. It also holds the inspector's two arithmetic claims about a fade, both of which read as plausible while being wrong: a tempo fade's seconds are checked against a closed form derived independently of the per-tick walk that produces them, because `$E3` is the one command whose duration cannot be priced at the tempo in force; and every fade command is checked to report a duration of 0 as dropped rather than instant, which is what the driver does with it. It pins `commands/in-force.ts` as well: that every VCMD and every named letter has a scope, since a table that quietly loses a row is a command the roll silently stops drawing; that `<` and `>` are never commands at all, where reading `LETTER_NAMES` would suggest they are; and that the parse-time half — `q`, `h` and `@21`-`@29`, the ones that emit nothing for a walk to address — carries forward, supersedes, stops at a channel boundary, starts above the first marker on the starting channel — the lowest `#N` the song declares, where the compiler starts writing, so a `q` or a drum `@` written there reaches that channel's first note — clears `h` at every marker including one re-entering its own channel, keeps the drum slot as the parser keeps `instrument[channel]` — the `[ ]` copy, the one-drum clearing off `#6`/`#7`, a `$DA` that writes nothing — and covers **only** commands the compiler's map does not, since a command answered twice would draw two glyphs for one setting. It also pins that the label and the clock share **one** model of a fade: `tempoFadeSeconds` is a sum over `tempoFadeSteps`, the run has one entry per tick and never reaches the target it snaps to, and `$51` wraps `t255` to a stop rather than to 256. ## `harness.ts`

`check`, `summarise`, `failureCount`, `SPC_ASSETS` and `stubFetch`. Use them rather than writing
another copy.

`stubFetch` reproduces two dev-server behaviours deliberately, because between them a missing sample
file surfaces as "invalid BRR length 2205" rather than a 404:

1. paths are decoded with `decodeURI`, which leaves `%40` untouched, so an over-encoded `@` never
   resolves to a real file;
2. an unresolved path is answered 200 with index.html, not 404 — so code that trusts `response.ok`
   gets HTML where it expected bytes.

A harness that threw on a missing file instead would pass while the browser failed.

## What none of them cover

**Angular templates.** Neither these nor `npm run typecheck` run the template compiler, so a bad
binding (`viewBox=` instead of `[attr.viewBox]=`) passes `npm run check` and fails only at
`npm run build` / `npm start`. Run one of those before believing a UI change.

## Establishing fidelity

`Compare-Spc.ps1` and `Compare-SongBin.ps1` diff output against a real AddmusicK build, region-aware
so ID666 noise does not drown the real differences. Those are what establish fidelity; the harnesses
only catch gross breakage.

`Compare-SongBin.ps1` is the sharper of the two: AddmusicK writes `asm/SNES/bin/musicXX.bin` for
every song it compiles, and past its 12-byte RATS header that file is exactly the blob this editor's
`.bin` export produces. Same song, same load address, so every difference is a real compiler
difference rather than a layout artefact. Run it with one argument to read the header and see which
address to compile at.
