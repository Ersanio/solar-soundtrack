Solar Soundtrack

Write it, hear it, edit it, export it — without leaving the tab.

A browser-based AddmusicK 1.0.11 music editor. It compiles your MML to N-SPC song data, assembles a playable .spc, and plays it through an emulated SPC700 — all in the browser, with no AddmusicK install, no ROM and no server.

What this is

AddmusicK is the custom music tool SMW Central uses, and this is a complete editor built around it. It is not a wrapper that shells out to AddmusicK.exe — the compiler is a port of AddmusicK 1.0.11's own Music.cpp, running in the page, and the SPC700 is emulated beside it. So the song you hear is compiled by the same rules the real tool compiles by, and played by the same chip your port will end up on.

It reads the same target markers AddmusicK does:

Marker What it selects
#amk 4 AddmusicK 1.0.9 and later — what you almost certainly want
#amk 2 AddmusicK 1.0 to 1.0.8
#amk 1 The AddmusicK beta
#am4 Addmusic 4.05
#amm AddmusicM
#amk 3 Rejected, with AMK0402 — Codec's beta is not implemented in AddmusicK itself either

It is a static site, so there is nothing to install and nothing to keep updated. It also installs as an app and works offline once it has loaded. What it does need is a browser with AudioWorklet and WebAssembly — any current Firefox, Chrome, Edge or Safari has both. Without WebAssembly it will tell you so rather than failing quietly.

What it fixes

Porting music with Addmusic has always been one of my favourite things to do in this hobby. What was never fun was the loop around it: to actually hear a port you had to insert it into a ROM, open an emulator, and go to the level that plays it. Change a note, and you do all of it again. AddmusicK's porter mode makes that easier, but it still means switching windows.

So the idea was one tool for everything, and the loop closes to nothing:

The usual way Here
Install AddmusicK, keep a clean ROM to hand Open a URL
Insert the port into the ROM to hear it It is already playing
Open an emulator, find the level that plays it Press Space
Change one note; repeat all of the above Hot Reload puts the edit into the running song at the position it had already reached. The music never stops.
Wait through the intro to reach bar 40 Drag the timeline. Seeking is exact, to the tick
Comment a channel out and recompile to hear the rest Mute and solo per channel, instantly
Read a compiler error, then go hunting for it The offending character is underlined in place, with a code and a sentence saying what is wrong
Guess whether it still fits in ARAM A meter in the top bar, exact to the byte
Write eight $F5 coefficients and hope Draw the curve you want and let it fit them
Read MML to work out what the arrangement is doing A piano roll over your actual MML text, editable in place

AddmusicK also has room to grow past SMW, in my opinion: the same engine has potential for other games and for homebrew, and there is a huge library of music already written for it.

What you get

Compile as you type

There is no compile button, and no manual reload. Every keystroke recompiles, and with Hot Reload on the running song is swapped out at the position it had already reached — so you keep editing and the music keeps playing.

An editable piano roll

Draw, drag, stretch, copy, quantize and delete notes, and the MML is rewritten to match — your MML, with your spacing and your comments left where you put them. It edits the song as written: loops stay loops, and every pass of one is drawn and edited in place rather than unrolled behind your back.

A playhead that is the truth

The highlighted note is the note you are hearing, in every channel, because the playhead follows the driver rather than estimating from the tempo byte. Not one second of it is predicted.

Hear one note in context

Click a note in the roll and you hear that note, at that point in the song, with the rest of the arrangement still sounding under it — its instrument, its volume, its echo, its pitch slide. Click a loop's box and you hear that whole pass. The song being played is never disturbed.

An exact ARAM budget

A meter in the top bar and a table under Build: driver, song, samples, echo buffer, free. It needs no guesswork, because everything AddmusicK occupies before your song is physically present in the driver image the editor loads.

It is a shade stricter than AddmusicK, which reserves nothing for the echo write and would let samples run into it.

An echo FIR designer

The eight coefficients of $F5 are the least readable thing in the language, so put the cursor on one and you get a frequency-response plot, named presets — including Super Mario World's own filter, verbatim — a dark-to-bright tone control, and FIRcon-style draw-a-curve-and-fit.

It plots the echo tail repeat by repeat, since the filter sits inside the feedback loop and each pass is filtered again; it shades the region below about 2 kHz where eight taps at 32 kHz have no real say; and it warns when the feedback and the filter together make an echo that builds instead of dying away.

A command inspector

It explains whatever the cursor is sitting on, in real units: t54 as a tempo in BPM, @2 as the sample it actually plays, $F1 as a delay in milliseconds and a buffer size in KiB. Vibrato, tremolo and pitch bends are drawn as shapes; ADSR and GAIN get an envelope graph and presets.

Everything it shows, it can also edit — and the edit is a splice, not a rewrite.

A command timeline

A strip under the roll holding nothing but commands, on the song's own timeline: every t, v, y, @ and echo write, on the tick the driver actually reads it. It is the one place the whole song's commands can be read in the order they run. Drag one to move it; right-click to delete it.

Diagnostics that point at the character

165 codes: 158 AMK ones AddmusicK itself reports, and 7 SST ones it has no opinion about. The span lands on the offending character rather than merely near it — even through a "name=value" replacement, where the error is attributed back to where you wrote it.

It tells you when the driver cannot keep up

The driver runs at most one tick per pass of its main loop, so a busy song at a high tempo simply gets fewer ticks than it asked for. One channel at t254 reaches 99.6% of its 498 ticks a second; eight channels reach about half, and a real eight-channel t254 song reaches 46%.

No formula predicts that, so the editor plays your song silently on a worker and times it. A SNES drops the same ticks — this is a fact about the song, not about the editor.

Monitoring that does not lie

Mute and solo work on channel volume, deliberately not on the driver's own $5E. A disabled channel makes each pass of the main loop cheaper, so muting seven voices on a t254 song speeds it up by 29% — and a mute that plays your music faster is telling you something untrue about it.

A sample library

Import .brr files or whole .bnk banks, audition any of them on the spot, see what each costs in ARAM, and mark the ones to keep loaded even when the song never plays them — which is what global songs and sound effects need.

The waveform drawn is the waveform the player will produce: the decoder is a transcription of the same core that does the playing.

Export

A finished .spc with its ID666 tags, or the raw song-data .bin — which past AddmusicK's 12-byte RATS header is byte-for-byte the same file AddmusicK writes to asm/SNES/bin/musicXX.bin. That is what makes it diffable against the real tool.

Yours to recolour

Five theme presets, or set any of the twenty-five colours yourself — the chrome, the eight channel colours, and the source view's syntax colours one by one. Nothing here says anything with colour alone, so you can put two channels on one hue and break nothing.

Why you can trust the output

The whole point is that a song written here goes into AddmusicK. So a divergence in either direction is a bug:

More permissive than AddmusicK is the dangerous one — it compiles here, plays here, and then the real tool refuses it. Stricter than AddmusicK is merely annoying, but still wrong: it rejects a song that works.

Which means being friendlier is never a reason to widen what is accepted. Where AddmusicK is case-sensitive, so is this: #Title is not a title, "kick.BRR" is not a sample, and #DEFINE is not a define. Where AddmusicK is unhelpful, so is this — an unknown #directive is read as music, and a * with no loop before it emits a call to nowhere, because that is what the reference does.

What backs that up:

  • A line-by-line audit. Every symbol in the parser, preprocessor and linker was mapped to its C++ counterpart and both sides read. A finding had to carry a file:line on both sides, a reproducer of ten lines or fewer, and an observed result from actually running it. All twenty-three confirmed divergences are fixed, each with a test written before the fix and failing without it.
  • One deliberate divergence, and it is #path: it is read, validated, and applied to nothing, because a directory prefix has nothing to mean in a library that is one flat list of names. You are told about it (SST0504), and AddmusicK still accepts the directive.
  • Fourteen byte-level harnesses run on every push, covering the compiler, the scanner, SPC assembly, BRR decoding, the echo FIR, the envelope maths, the audio worklet, the piano roll's edits, and the whole MML → SPC → PCM chain through the real emulator.
The honest limit

Those harnesses catch gross breakage. What actually establishes fidelity is diffing the output against a real AddmusicK build, which is what scripts/Compare-Spc.ps1 and scripts/Compare-SongBin.ps1 are for. If you have AddmusicK to hand, that is the single most useful thing you can do as a tester: compile a port both ways and diff the two .bin files. Any difference is a real compiler difference, and I want to hear about it.

Your first session

  1. Open the editor. It opens on the Source tab with whatever you last had; a fresh visit gets an empty document.
  2. Paste your MML in, or type something small to feel it out. The status bar says whether it compiled, and the Problems section fills up if it did not.
  3. Press Space — or Play in the top bar. It compiles, assembles an SPC and starts playing.
  4. Turn on Hot Reload and edit while it plays. Change a v, a y, an @, the tempo — the song reloads at the position it had reached and carries on.
  5. Put the cursor on a command and read the Inspector in the sidebar. Try it on a $F5 coefficient to get the FIR designer, or on an $ED for the envelope tuner.
  6. Open the Piano roll tab. Click notes to hear them in context, drag one to move it, and watch the MML change under you in the Source tab.
  7. Check the ARAM meter in the top bar, and click it for the full table.
  8. Export. Export .spc gives you something you can play anywhere; Download .bin gives you the raw song data.
Getting your work out

There is no MML file open or save yet. Your draft is kept in this browser's local storage and your sample library in IndexedDB, so closing the tab does not lose them — but clearing site data will, and there is no file on disk until you make one. To take a song to AddmusicK, select the text in the Source tab and copy it into your own .txt. Back up work you care about.

Grid, Snap and Edits

Three settings on the roll's toolbar decide how a drag lands, and they are worth knowing before you wonder why a note went where it did.

Dragging moves a note by whole steps; it does not pull it onto the grid. A note written a little before the beat is meant to be there, and dragging it a bar later leaves it a little before that beat too. Drawing a new note is the exception — it has no position of its own to keep, so it lands on the grid where the ghost said it would. Alt + Q is the one thing that pulls a note onto the grid, which is what quantizing is for.

Stretching does not use Snap. A length lands on the note values themselves — a whole, a half, a quarter, an eighth and their dotted forms — because a note in MML is a duration rather than a region on a timeline. The bubble that follows the edge says which one you are on, and reads the note as it will be written.

A channel plays one note at a time, so two notes can never overlap, and Edits is where you say what a gesture does about that:

Mode What happens when notes would overlap
Overwrite The note you are placing takes the ticks. What was under it keeps whatever it did not cover — the ticks being taken are hatched in red while you drag, and what survives is drawn as a striped outline. A note you land wholly inside comes back as two, at the same pitch. This is where a fresh roll starts.
Insert The notes in the way move out of the way, in the direction you are dragging, and the notes they run into go too. It can run out of room, and says so.
Strict Never writes an overlap. The bar turns red, the clashing ticks are washed red down the roll, and letting go changes nothing.

It is one rule for every gesture — drawing, dragging, nudging with the arrows, stretching an edge and Alt + Q alike — so where you grabbed the bar does not change the answer.

Loops

A loop is one run of text the driver plays many times, and the roll draws it that way: every pass is on screen, each as a box around the rows its notes span, washed in the channel's colour.

What you see What it means
A dashed edge The pass standing where the text is — the group an edit rewrites.
A dotted edge This plays again here — a repeat, or a (n) or * recall.
A solid edge The group is selected.

An edit to any pass edits them all, because there is only one text. Click the third pass of a looped note and every pass rings, with the one you clicked solid and its siblings stepped back. That holds across channels too: a loop declared on #0 and recalled on #1 is one body both voices play, and editing it from either changes both.

Gesture What it does
Click a box's edge Selects the loop's whole group, closes every box of that body up into one solid line, plays that pass, and names it in the loop inspector.
Drag the top or bottom rule sideways Moves that pass along the song: rests open in front of it and the recall splits. Dragging back closes the gap and joins the two halves up again.
Drag the top or bottom rule up or down Transposes the whole body, one row per semitone, every pass moving together. A loop written inside it goes too; one merely called from inside does not.
Drag the right end Changes the body's own length — a rest goes on its tail, or its trailing rests come off.
Drag the left end Moves where the loop begins while the notes inside stand still, so the first pass plays exactly where it did and only the passes behind it slide. It needs rests in front of the loop to grow into.
Draw inside any pass Writes into the body once, between the brackets, and it appears on every pass — the ghost's siblings show it landing everywhere before you let go.

Which of the three the drag is settles the moment it starts moving and stays settled, so wandering off the straight does not swap one edit for another. The pointer's cursor says which one a press will start before you commit to it.

Making one

Select the notes you want repeated and press Loop in the command palette — it is in the sidebar's Inspector, under Add a command. The brackets go round the whole run, nothing between them is rewritten, and the loop opens playing twice with its repeat count selected so the number is one keystroke away. A fresh loop is named with the lowest number the song is not already using, so it can be recalled later with (0)3.

Press Loop inside a loop and you get a subloop instead, and vice versa — AddmusicK holds one [ ] and one [[ ]] at a time, and the readout says which the button is about to write. Loop call plays a loop you have already written, again from here; it names the nearest one above the cursor, because AddmusicK reads a song in order and a call can only reach a loop it has already met.

The loop inspector names the loop the cursor is in, under the command inspector: one card per loop, with its Repeats to change, which loop a call plays, and an offer to name a body that has not got one. With the cursor in no loop the panel is not there at all.

Escape, or a click outside Closes either popover.

Only the colours you actually move are stored, so changing one still leaves the rest following the app as it changes.

What it will not do

Stated plainly so you do not spend time filing these. If one of them is in your way, say so — knowing which limits actually bite is exactly what a beta is for.

The piano roll turns some channels away

It edits your MML as written, and refuses rather than guessing wherever what is written and what is played are not one to one. The toolbar says which in words.

What it refuses Why
A channel written through a "name=value" replacement One written note is not one played note, and an edit has no single place to go.
A channel using { } triplets Every length is two thirds of what it says.
A song using #halvetempo Same reason.
A song using a legacy & This one refuses the whole song. It is an operator rather than a command, so nothing above the compiler can say which channel it is on, and the bend it compiles to takes its length from the note before it. Write it as the $DD it compiles to and the roll can see it.
A loop and a subloop that cross One opens inside the other and closes outside it, which plays neither construct as written.
An unterminated $E6 $00 Nothing closes it.
A * or (n) replaying a remote code body The roll cannot line that up with what plays.
A channel you cannot hear Mute it or solo another part and its notes go dim and stop answering the pointer. Unmute it and it takes edits again.

Ordinary loops are not on that list. A [ ], a [[ ]], the same thing written as $E6, a * and a (n) call are all drawn and edited in place — see Loops above. This changed, so older notes may say otherwise.

Everywhere else

  • No chords. A channel plays one note at a time. What a gesture does about an overlap is the Edits setting, and it is the same answer for every gesture.
  • No MML file open or save. Copy and paste is the way in and out for now.
  • #path does nothing. It is read and validated and applied to nothing, because the library here is one flat list of names. This is the one deliberate difference from AddmusicK, and you are told when a song uses one.
  • Some songs get no predicted length. A song with a tempo fade, or a t that runs more than once, has no length the compiler will state — AddmusicK gives up on the same songs, and this reproduces that. The measured clock covers it for the transport.
  • The echo hazard check has a blind spot. A $F1 in one channel and a $F5 in another do interact on the real chip, and that pairing is not caught. Neither is a $F5 and a $F1 inside the same macro.

Error codes

Everything the compiler has to say about your song carries a code. They are listed in Problems, pinned to the bottom of the sidebar; click one and it takes you to the text that raised it. This is what all 165 of them mean.

The prefix says whose finding it is, not which part of the app noticed. AMK is a condition AddmusicK 1.0.11 itself reports, ported from its source with its own wording — see one of these and the real tool would say the same thing about the same song. SST is Solar Soundtrack's own finding, on something AddmusicK has no opinion about at all: it will not warn you, and it will not stop you.

Severity What it means
Error The song does not compile. Nothing is produced and nothing plays.
Severe It compiles cleanly and then misbehaves when played — music that never sounds, an echo that grows instead of fading, a tempo the driver cannot keep.
Warning It compiles and it plays. Something is wasteful, imprecise, or will not survive an older AddmusicK.
Notice Worth knowing and nothing more. There is exactly one.

A code never changes meaning, so quoting one in a bug report is enough to say exactly what you saw. The number bands are AddmusicK's own ordering rather than a grouping you need to learn; the headings below are.

Solar Soundtrack's own

Seven findings AddmusicK does not make. Six are about what a song does rather than about whether it builds, so real AddmusicK will compile every one of these without comment.

Code Severity What it means
SST0301 Error The ARAM address the song was asked to build at is outside the 64 KiB address space. Nothing you can write causes this.
SST0500 Severe Custom $F5 coefficients and the feedback in force make the echo grow instead of fade, so the song gets louder and distorts. Lower the feedback, or the filter's gain — the FIR designer plots both.
SST0501 Severe The same, through one of $F1's two built-in tables. Lower the feedback, or select filter 1, which cannot run away on its own.
SST0502 Severe A channel holds more music than the song is long. The driver ends the song the moment any channel runs out, so everything past the shortest channel is dropped in silence — nearly always a loop count or a note length out by a factor of two.
SST0503 Severe The driver cannot run the song as fast as it is written, so it plays slower than the t says. Measured, not predicted — see the status bar, which shows the two rates side by side.
SST0504 Notice The song uses #path, which does nothing here: the sample library is one flat list of names. This is the one deliberate difference from AddmusicK, and it is why you are told.
SST0505 Error A replacement whose value contains its own name, so expanding it never finishes. AddmusicK grows its buffer forever on the same song rather than stopping, so there is no run to be faithful to.

Reporting a bug

This is the part I actually need. Please test it functionally and tell me what breaks — bugs, ideas and feature requests are all wanted.

What makes a report easy to act on:

  • The MML. The smallest song that still shows it, pasted in — this matters more than anything else.
  • What you expected, and what happened instead.
  • Your browser and platform, since the audio path differs between them.
  • The commit, from the GitHub icon in the top bar, so I know which build you were on.
Especially valuable

Two classes of bug are hard for me to catch and easy for you to trip over. The first is anything visual that is simply missing — a blank icon, a bar with no glyphs, a graph that does not draw — because none of the automated checks run the template compiler, so that kind of fault reaches production. The second is output that differs from real AddmusicK: if you can compile a port both ways and diff the two .bin files, any difference is a genuine compiler bug.

GitHub Issues is the best place, and it is also where the ideas, planned features and known issues live. Failing that, the best way to reach me is a Discord DM — I am in the SnesLab and SMW Central servers — or a private message on SMW Central.

About the code

Effectively all of the code in this repository was written by AI. It works, it is tested, and I have read and steered it to the best of my abilities, but it has not had the kind of human touch a codebase deserves before people build on it. So for now I would much rather you tested the application and reported bugs than tried to contribute code — I am working on making it maintainable, but it is slow. If you are planning something large, please talk to me first.
